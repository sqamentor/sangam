# sangam-packs: government approval core, government domain packs, universal packs and sector packs

Owner: WS-PACKS. Base package `org.sangam.packs`. Binding rules: `../ARCHITECTURE.md`. Requirements: `../../SANGAM.md` IX.3-IX.5, IX.8, X.4, GOV-1..12; patterns: `../../spike/GOV-PATTERNS.md` (GP-01..GP-55) and `../../spike/results/PREMIUM-AND-UNIVERSAL-SCOPE.md` (UP-01..UP-22); sector packs: `../../spike/results/SECTOR-WORKFLOWS.md` (SEC-<SECTOR>-nnn).

**Contents:** 130 packs, 183 BPMN processes, 154 DMN decisions, 4 CMMN cases, 476 bilingual (English / Hindi) forms, seed seats and roles per pack, 65 Java source files (SPI, ports, simulator, delegates, workers). All models deploy on Operaton 2.2.0 with XSD validation and history-TTL enforcement on, every call activity resolves, every startable process reaches its first wait state, and the four pilot packs run end to end on the simulator (see "Tests").

## 1. Layout

```

  port/      ConnectorGateway (+ request/result), SeatDirectory, BusinessCalendar, PackAuditSink, BatchLedger,
             LedgerStore, PackRuntime (port holder with simulator defaults)
  sim/       SimulatorConnectorGateway, InMemorySeatDirectory, WorkingDayCalendar, LoggingAuditSink,
             InMemoryBatchLedger, InMemoryLedgerStore
  core/      delegates and listeners of the approval core (used by every pack)
  gov/       domain delegates (merit list, waitlist, scroll / stock matching, hearings)
  universal/ EventWindowDelegate
  worker/    PackWorker, PackWorkers (external-task topics), EmbeddedWorkerRunner
src/main/resources/
  META-INF/sangam/packs.idx           index of pack manifests
  packs/<pack>/pack.json              SangamPack descriptor (manifest)
  packs/<pack>/*.bpmn | *.dmn | *.cmmn models (BPMN with diagram layout for the modeller)
  packs/<pack>/forms/*.form.json      bilingual forms (formKey "sangam:<pack>/<name>")
```

The models, forms, seeds, manifests and this README are generated by `tools/packgen` and must not be edited by hand: change the generator, run it, and check with `python tools/packgen/main.py --check` (see `tools/README.md`).

## 2. Pack SPI and deployment

- A pack is a `SangamPack` whose `PackDescriptor` gives id, version, display names (en / hi), domain, main processes, resources (BPMN, DMN, CMMN, FORM, SEED), seed roles and seats, connectors with capability class and government tag, covered ids (GP / UP / AC / J / R / K) and acceptance scenarios (given / when / then, start variables, expected `caseState`).
- `PackRegistry.discover()` reads `META-INF/sangam/packs.idx` manifests (`ManifestPack`) and `ServiceLoader` packs (department jars). `deploymentOrder()` sorts by `dependsOn` (every government pack depends on `sangam.core`).
- `new PackDeployer(engine, registry).deployAll(tenantId)` deploys one engine deployment per pack (`pack:<id>@<version>`, duplicate filtering on), forms and seeds included, after `ModelGuard` checks. `tenantId = null` deploys shared definitions; a tenant id deploys a department's overrides, which `Decisions` prefers (GP-37); the manifest's `tenantOverrides` for that tenant replace the shared tables of the same key in that deployment. Deploy tenants with `deploy(packIds, tenantId)`, which includes the dependencies: Operaton resolves the call activities of a tenant process only within the same tenant. With the in-memory seat directory the seeds are loaded too.
- `PackMigrator.migrateAll(processKey, fromVersion, toVersion, tenant)` migrates running cases (GP-20); activity ids are kept stable across pack versions for this.
- A case is bound to `packVersion = <id>@<version>` at start (R43, K10).

Side exits in every pack: interrupting event sub-processes on `sangam.withdrawCase` (initiator) and `sangam.cancelCase` (authorised) call `sangam-core-cancellation`. SLA-guarded tasks carry a 75 % warning timer and a breach timer (escalate up the reporting seats, or deemed approval / refusal by the system principal on behalf of the seat). Approval tasks carry, in order, the SoD guard, the power guard, the payload binding and the actor recorder.

## 8. Integration notes (ports the integrator wires in `sangam-server`)

Install the production adapters once at start-up: `PackRuntime.install(PackRuntime.defaults().withGateway(..).withSeats(..).withCalendar(..).withAudit(..).withBatches(..).withLedgers(..).withClock(..))`. Until then every port runs on its simulator / in-memory default.

| Port | Implementer | Contract |
|---|---|---|
| `port.ConnectorGateway` | WS-INTEGRATION | `submit` writes the outbox in the caller's transaction and returns PENDING (or a stored first result for a repeated operationId; a different payload hash is IDEMPOTENCY_PAYLOAD_MISMATCH); the relay delivers `sangam.operationResult` correlated on `operationId`; `query` is read-only; `lookup` for classes a/b; `cancel` for VI.5; `openReconciliation` creates the O04 item; `capabilityOf` per connector (A-8 default c). Connector ids used by the packs are listed in each `pack.json`. |
| `port.SeatDirectory` | WS-SECURITY | effective-dated postings, additional charge and delegation; seat ids are the candidate groups; `seatForRole` walks the office hierarchy; `escalationSeatOf` is the reporting seat. |
| `port.BusinessCalendar` | WS-ENGINE (SangamClock + tenant holidays) | specs `nWD`, `nD`, `nH`, `nWH`, ISO durations; UTC instants. |
| `port.PackAuditSink` | integrator (audit chain, same transaction) | X.4.0.3 event names and fields. |
| `port.BatchLedger` | WS-ENGINE / persistence (product table) | idempotent per (batch, round, item), first outcome wins. |
| `port.LedgerStore` | WS-ENGINE / persistence (product table) | postings idempotent by reference; reversal by reference. |
| `worker.PackWorkers` | WS-REST worker API / WS-SDK | topics sangam.docs.bulk, sangam.rpa, sangam.pfms.paymentFile, sangam.ai.extract; capability class per topic. |

Requests to other workstreams: (1) WS-REST should set `actingPerson` / `actingSeat` task-locally and `presentedPayloadHash` on approval completions, and map `422 SOD_VIOLATION`, `422 POWER_LIMIT_EXCEEDED`, `409 APPROVAL_INVALIDATED` from the listener messages to problem+json; (2) WS-INTEGRATION should honour the message names above; (3) the engine configuration may keep `enforceHistoryTimeToLive = true` (every model sets a TTL); (4) WS-ENGINE's deploy-time multi-instance threshold and `ModelGuard.MAX_MULTI_INSTANCE` (50) should agree.

## 11. Notes and known gaps

- Thresholds, fee tables, power limits, timelines and roles in the DMN tables and seeds are SYNTHETIC pilot values (marked in each table); departments replace them with their delegation-of-powers orders and notified timelines.
- Works sanctions follow estimate > technical sanction > administrative approval by default; the order is pack configuration in the DMN `works-config` (output `worksSanctionOrder` TS_FIRST / AA_FIRST): a row per office for one department, or a tenant override deployment (sample: `overrides/state-b/works-config.dmn`, AA first).
- Event-subprocess timers that are armed at scope start use literal durations (UP-16 leaver deadline PT4H, UP-19 obligation cycle R/P30D) because no variable exists yet at that moment.
- CMMN timer listeners are not used (Operaton 2.2.0 limitation found in the spike); CMMN variants run their SLA in a blocking BPMN process task.
- The simulator answers queries with plausible defaults (budget 1 crore, L1 bidder, confidence 0.82); real adapters must return the same data keys (see each `ConnectorCallDelegate` result prefix).
- Statutory durations that depend on day arithmetic not expressible in JUEL (for example "decide within 40 days of receipt" after a third-party window) are approximated by resetting the case clock to the remaining period.
- Sector packs (`sec.*`) carry SYNTHETIC grids (credit policy, underwriting, delegated powers, commissions, licences by category) and the statutory timelines found in SECTOR-WORKFLOWS.md; timelines marked "verify" there must be checked against the regulator's current text before go-live and are changed by a tenant DMN override, not by editing the models.
