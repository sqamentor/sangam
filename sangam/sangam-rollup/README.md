# sangam-rollup (SCALE)

National / cross-cell read model (port 8095, management 8096), own database, counts and identifiers only. Design:
`../SCALE-ARCHITECTURE.md` section 8.

| File | Covers |
|---|---|
| `RollupProjector.java` | Idempotent projection: dedup row + sharded counters for every hierarchy prefix in one transaction (VI.2.3 rule 4); per event (8.2) or as one pre-aggregated micro-batch per ingest array (M-063, 8.4 b); dedup retention |
| `RollupEvents.java` | What an event counts, defined once for both paths: validation, UTC day, deltas (`process.open` gauge, per-definition metrics), explicit metric events, the scope check, the forwarded ("cut") node |
| `RollupBatch.java` | In-memory pre-aggregation of one batch: deltas summed per (node, metric, day), keys sorted (one lock order), the row saving measured |
| `RollupWriter.java` | The row writes (dedup, counters, nodes, feed, pending upstream deltas), one portable SQL text each |
| `RollupUpstreamEmitter.java` | State-level tier (M-063, 8.4 a): pending deltas become explicit metric events in `RU_UPSTREAM_OUTBOX` (guarded decrement, exact) |
| `RollupUpstreamSender.java` | Delivers the tier's events to the upper roll-up (at least once; parks poison events, retries outages with back-off) |
| `RollupMetrics.java` | Micrometer measurement hooks for SG-15 / T-SCALE-10 (see below) |
| `RollupController.java` | `POST /api/v1/ingest` (CloudEvent or array; 422 for a single rejected event = poison), `GET /api/v1/rollup/metrics?node=&from=&to=`, `/series`, `/children`, `/feeds` |
| `RollupConfig.java` | Own Liquibase changelog (`db/changelog/rollup`, five dialects, generated by `../sangam-control-plane/tools/generate_scale_changelogs.py`, `--check` verifies; before it runs, `DatabaseIdentity.requireScaleDatabase` refuses MariaDB, CockroachDB, YugabyteDB and any other database by a `SCALE_DB_*` code, decision 384, `RollupConfigDatabaseCheckTest`); tokens CELL (ingest), TIER (ingest incl. explicit metrics), DASHBOARD (read) |

## Micro-batch pre-aggregation (M-063, 8.4 b)

`sangam.rollup.pre-aggregate` (default `true`): an ingest array is projected in one transaction. The ids already
projected are read once (`IN` lists of 100), the new ones inserted together, and their deltas summed per (node,
metric, day) before each distinct row is written once, on one shard per batch. Dedup rows and counters commit
together, so redelivery stays exact. If a concurrent writer inserts one of the batch's ids or the first row of one of
its keys in between, the batch rolls back and is projected event by event (counted in `sangam.rollup.batch.fallback`).
A single event, or `pre-aggregate: false`, uses the 8.2 per-event path.

## State-level tier (M-063, 8.4 a)

One roll-up per state or region, the national roll-up fed by their aggregates. Same image, configuration only:

| Key | State instance | National instance |
|---|---|---|
| `sangam.rollup.scope` (`SANGAM_RU_SCOPE`) | `IN/RJ`: events outside are rejected | empty |
| `sangam.rollup.upstream.url` (`SANGAM_RU_UPSTREAM_URL`) | the national `.../api/v1/ingest` | empty (top tier) |
| `sangam.rollup.upstream.token` (`SANGAM_RU_UPSTREAM_TOKEN`) | a national token with role TIER | |
| `sangam.rollup.upstream.instance-id` (`SANGAM_RU_INSTANCE_ID`) | for example `rj-1` (at most 16 characters; the national `/feeds` row) | |
| `sangam.rollup.upstream.depth` (`SANGAM_RU_UPSTREAM_DEPTH`) | deepest level forwarded; default one below the scope (districts) | |
| `sangam.rollup.upstream.interval` / `send-interval` / `max-batch` / `timeout` | PT1M / PT5S / 200 / 10s | |

The state's cells post to the state instance (their relay URL), not to the national one. The state projects as usual
and, in the same transaction, adds every delta to `RU_UPSTREAM_PENDING` under the event's ancestor at the forwarded
depth. Every interval the emitter moves the pending deltas into `RU_UPSTREAM_OUTBOX` as **explicit metric events**:

```json
{"specversion":"1.0","id":"<uuid>","source":"sangam://rollup/rj-1","type":"sangam.rollup.metric",
 "sangamcell":"rj-1","sangamtenantpath":"IN/RJ/RJ-JPR","data":{"metric":"process.start","day":20261112,"delta":37}}
```

The national roll-up adds `data.delta` to `data.metric` on `data.day` for the path and every prefix of it, exactly as
for a stream event, so its totals at and above the forwarded level equal the states' totals. Levels below it (the
hospitals) stay in the state roll-up. Only a TIER (or ADMIN) token may send an explicit metric event; a
`sangam.rollup.metric` event without `data.metric` keeps the 8.2 meaning (counted once).

Exactness: the decrement of a pending row is guarded by the value read, and commits with the outbox row; the national
roll-up deduplicates on the event id, so the sender may redeliver. Outages are retried (2^attempts s, at most 5 min);
a 400/413/415/422 answer to a single event parks it (`parked = 1`), never drops it. A wrong token or URL (401/403/404)
is retried, not parked.

## SG-15 / T-SCALE-10 measurement hooks (written, not run)

On `/actuator/prometheus` (management port):

| Meter | Reads |
|---|---|
| `sangam_rollup_ingest_seconds{mode="batch"\|"event"}` | latency of one ingest call per path |
| `sangam_rollup_events_total{outcome}` | projected / duplicate / rejected events |
| `sangam_rollup_batch_events`, `sangam_rollup_batch_rows`, `sangam_rollup_batch_rows_naive` | events per batch; row writes made; row writes the per-event path would have made (ratio = the 8.4 b saving) |
| `sangam_rollup_batch_fallback_total` | batches replayed event by event after a race |
| `sangam_rollup_upstream_events_total{result}`, `sangam_rollup_upstream_send_seconds` | the tier feed (queued, sent, parked, retry) |

The test phase measures with them (SCALE-ARCHITECTURE 11, T-SCALE-10 and the 8.4 capacity claim): events/s per roll-up
database with `pre-aggregate` on and off, the rows/naive ratio, and national totals against per-cell SQL counts after a
double replay through a state tier. Unit and H2 tests: `RollupEventsTest`, `RollupBatchTest`,
`RollupMicroBatchH2Test`, `RollupTierH2Test` (written in Wave 3, not run yet).

Dependencies: Spring Boot 4.1.2 starters (webmvc, jdbc, actuator, security), Liquibase 4.33.0, HikariCP (Apache-2.0);
JDBC drivers as the control plane.
