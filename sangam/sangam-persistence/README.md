# sangam-persistence (WS-ENGINE)

The Sangam product schema: a Liquibase **4.33.0** master changelog with one **formatted-SQL changelog per dialect**
(D-7, R12, D-54, A-15) and a small Java API, `SangamSchema`, that applies it. The Operaton `ACT_*` tables are owned by
the engine and are not created here; the two MySQL engine schema patches (P-1, P-2) are a separate changelog.

| Entry point | Use |
|---|---|
| `db/changelog/sangam-master.xml` | master; includes the 5 dialect files, each changeset tagged `dbms:` |
| `db/changelog/sangam-master.yaml` | YAML wrapper that only includes the XML master (Spring Boot's Liquibase looks for YAML). Same changeset ids either way |
| `db/changelog/sangam-engine-patches.xml` | P-1 / P-2 (MySQL; `runAlways`, idempotent), run **after** the engine built its tables |
| `db/changelog/<postgresql|oracle|mssql|mysql|h2>/sangam-0001-baseline.sql` | generated DDL, 286 tables (plus `ONB_RUN` in `sangam-0002-onboarding.sql`) + 10 column/index changesets |

**One source for five dialects.** The SQL files are generated by `tools/generate_changelogs.py` from one portable
table catalogue (`python -I tools/generate_changelogs.py`), so the dialects cannot drift. Never edit an applied
changeset: add a new catalogue entry with a new changeset id (Liquibase checksums).

Dialect rules: PostgreSQL `TIMESTAMP WITH TIME ZONE`/`BYTEA`/`TEXT`; Oracle `VARCHAR2(n CHAR)`/`RAW(32)`/`CLOB`;
SQL Server `NVARCHAR`/`DATETIMEOFFSET`, primary keys above 900 bytes are `NONCLUSTERED`; **MySQL 8.4 InnoDB,
`utf8mb4`/`utf8mb4_bin` on every table, `DATETIME(6)` UTC** (at least the DATETIME(3) floor of P-1; 6 because the core
`AuditChain` hashes microsecond timestamps), `source_id` key columns of `AUTH_GRANT_SOURCE`/`AUTH_MEMBERSHIP` are
`ascii_bin` so the keys fit the 3,072-byte limit; H2 (development only) uses `CHARACTER/BINARY LARGE OBJECT` and works
with `MODE=PostgreSQL`. Booleans are `SMALLINT` 0/1 everywhere.

## Java API

`org.sangam.persistence.SangamSchema`: `apply(DataSource)`, `apply(DataSource, contexts)`, `apply(Connection, changelog,
contexts)`, `applyEnginePatches(DataSource)`, `detect(Connection)`, `PRODUCT_TABLES`. Uses Liquibase's session lock
(`DATABASECHANGELOGLOCK`), so concurrent starts migrate once (R12). The same changelog runs from the CLI / a Kubernetes
Job: `liquibase update --changelog-file=db/changelog/sangam-master.xml`.

**Failed migration (R12 recovery):** each changeset is one table with its indexes and a `--rollback DROP TABLE`. On a
failure: read `DATABASECHANGELOG` (applied ids), fix the cause, run `liquibase release-locks` if the lock is stuck, and
run `update` again; a partly created table of the failed changeset (Oracle/MySQL DDL auto-commits) is dropped by hand
first. Rollback of the baseline: `liquibase rollback-count`.

## Generic modules (shapes converted by script)

134 tables were converted by script (`tools/import_module_schemas.py <sangam root> <block out> <report out>`, which
parses the modules' `*Schema.java` with `tools/import_java_ddl.py` and checks reserved words and key sizes) from: `sangam-config` ConfigSchema (CFG_*, 5), `sangam-ledger` LedgerSchema (LDG_*, 5;
`sangam-billing` has no tables of its own, it books on LDG_*), `sangam-registry` RegistrySchema (REG_* incl.
REG_PARTY_CONFIG, 33), `sangam-resources` ResourcesSchema (RES_*, 28), `sangam-geo` GeoSchema (GEO_*, 6), `sangam-field`
FieldSchema (FLD_*, 17), `sangam-case` CaseFileSchema (CF_*, 25), `sangam-programme` ProgrammeSchema (PG_*, 15).
`sangam-connectors-health` and `sangam-cell` define no tables; `sangam-control-plane` and `sangam-rollup` keep their own
changelogs. Changesets `0018-*` … `0025-*`; inline `UNIQUE` constraints become unique indexes `<TABLE>_UQn`. New type
tokens: `{date}` (DATE), `{num24_6}` (NUMERIC/DECIMAL/NUMBER(24,6); ProgrammeSchema's `{dec}`), `{num12_6}`,
`{vc80}`. Also added: `SEC_TENANT_KEY` (changeset `0026-01`, sangam-security reference DDL); `SEC_ORG_UNIT_NAME` was
checked against the reference SQL and matches.

**Shape check:** the six reserved-word columns found in the first pass were renamed by their owners
(`last_value` → `last_no` in CFG_SERIES, REG_METER, RES_BOOKING_SEQ, RES_TOKEN_SEQ; `LDG_BALANCE.distributed` →
`distributed_amt`; `CF_MEETING.mode` → `meeting_mode`), so no column is quoted on any dialect (the generator's
`QUOTED` fallback is empty). `REG_NUMBER_ALLOCATION`'s primary key is 902 bytes on SQL Server (> 900 clustered limit)
and is generated `NONCLUSTERED` (no functional change). The module changesets `0018-*`…`0025-*` were regenerated in
place before any release; a development database that applied the first pass needs `liquibase clear-checksums`.

No key exceeds MySQL's 3,072-byte index limit or SQL Server's 1,700-byte nonclustered limit; no constraint or index
name collides with an existing one.

## History partitioning (IR-8, optional)

`db/changelog/sangam-history-partitioning.xml` (context `partitioned-history`; **not** in the master) partitions
`ACT_HI_ACTINST, ACT_HI_TASKINST, ACT_HI_VARINST, ACT_HI_DETAIL, ACT_HI_IDENTITYLINK, ACT_HI_OP_LOG, ACT_HI_INCIDENT,
ACT_HI_JOB_LOG, ACT_HI_EXT_TASK_LOG` by `REMOVAL_TIME_`, monthly, 1 month back and 24 ahead. Run it after the engine
build: `SangamSchema.applyHistoryPartitioning(ds)`, or engine setting `partitionedHistory=true` /
`SANGAM_PARTITIONED_HISTORY=true`. Monthly maintenance: PostgreSQL `SELECT sangam_hi_maintain(24)`, Oracle
`EXEC SANGAM_HI_MAINTAIN(24)`, SQL Server `EXEC SANGAM_HI_MAINTAIN 24` (the server's leader may schedule it).

| Dialect | How | Limits |
|---|---|---|
| PostgreSQL 11+ | table rebuilt as `PARTITION BY RANGE (removal_time_)` + DEFAULT partition (NULL = running instances); rows copied; indexes re-created | the `ID_` primary key becomes a plain index and engine unique indexes become non-unique (a partitioned PK must contain the nullable partition key); a later partition cannot be created for a range already holding rows in DEFAULT, so run maintenance ahead; engine upgrade scripts that add UNIQUE indexes to these tables fail; conversion copies data (plan a window) |
| Oracle 19c+ | online `ALTER TABLE … MODIFY PARTITION BY RANGE … ONLINE UPDATE INDEXES`, partitions + `P_MAX` (holds NULL), row movement on | needs the **Partitioning option** (Enterprise Edition; included in 23ai Free); interval partitioning not usable (NULL keys); `ID_` PK stays a global index |
| SQL Server 2016 SP1+ | `SANGAM_HI_PF(datetime)` RANGE RIGHT + scheme; clustered index on `REMOVAL_TIME_`; PK re-created NONCLUSTERED on `[PRIMARY]` | other engine indexes not aligned → no partition SWITCH; NULLs in the first partition |
| MySQL 8.4 | **not provided** | InnoDB requires every PRIMARY/UNIQUE key to include the partitioning column, and primary-key columns must be NOT NULL, but `REMOVAL_TIME_` is nullable and the engine's PK is `ID_` alone; changing engine column nullability/keys would break Operaton's upgrade scripts. Use removal-time cleanup (R29) on MySQL |
| H2 | not applicable (development) | the changelog is a no-op |

Never drop history partitions by hand on tenants with legal holds (R61): use the engine's removal-time cleanup, which
honours holds through the product layer.

## Integration notes

- sangam-server: either let Spring Boot run `classpath:db/changelog/sangam-master.yaml` (then set
  `sangam.engine.apply-product-schema=false`) or let `SangamEngineFactory` apply it; never both with different paths.
  P-1/P-2 always run from the engine configurer after the engine build.
- The core `org.sangam.core.layer.Schema` DDL is now superseded by these changelogs for every environment; core
  `AuthorizationPolicy` inserts into `AUTH_EFFECTIVE` without `cond_key` (NOT NULL in the adopted shape): integrator to
  align core with sangam-security.

## Coverage check

`python -I sangam-persistence/tools/check_schema_coverage.py` (from `sangam/`) lists module tables no changelog creates; it must report 0 missing. `tools/add_missing_tables.py` converts them into new changesets. No column is quoted on any dialect (`ALARM_EPISODE.last_value` was renamed `last_no`).
