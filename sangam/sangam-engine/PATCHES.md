# sangam-engine: engine behaviour changes (patch ledger)

Base: `org.operaton.bpm:operaton-engine:2.2.0` from Maven Central, used **unchanged as a dependency** (ADR-D-16).
This ledger records every place where Sangam changes engine behaviour, so each upgrade can re-check it.

## Summary

| Kind | Count |
|---|---|
| Engine source or bytecode patches | **0** |
| Engine schema patches (DDL on `ACT_*` after the engine created them) | **2**: P-1, P-2 (MySQL only) |
| Behaviour changed through public extension points | B-1 … B-26 |
| Internal (`impl`) classes used | I-1 … I-19 (sangam-engine); every file that uses one, in any module, is on allow-list A or B |
| Reflection | 0 |

## Schema patches

| ID | What | Where | Why | Re-check on upgrade |
|---|---|---|---|---|
| **P-1** | MySQL: every `ACT_*` `datetime`/`timestamp` column with precision 0 → precision 3 (66 columns in 2.2.0) | `sangam-persistence/.../mysql/MysqlDatetimePrecisionPatch.java`, changeset `P-1-mysql-datetime-precision` in `db/changelog/sangam-engine-patches.xml` (runAlways), run by `SangamEngineConfigurer.afterBuild` | D-03 / FC-30: a lease was re-offered 200 ms early and a timer fired 300 ms early (spike ledger, MySQL (2)) | yes: upgrade scripts may add second-precision columns; the patch is idempotent |
| **P-3** (optional) | `ACT_HI_*` (9 high-volume tables) partitioned by `REMOVAL_TIME_` on PostgreSQL / Oracle / SQL Server; PostgreSQL drops the `ID_` PK in favour of a plain index | `sangam-persistence/.../sangam-history-partitioning.xml` (context `partitioned-history`), run by `SangamSchema.applyHistoryPartitioning` / setting `partitionedHistory` | IR-8, R29: cleanup and retention at volume | yes: engine upgrade scripts that add unique indexes to these tables fail on PostgreSQL |
| **P-2** | MySQL: every `ACT_*` table in utf8mb3 → `utf8mb4 / utf8mb4_bin`. String FKs touching the converted tables (46 in 2.2.0) are read from `information_schema`, journaled in `ACT_GE_PROPERTY` (`sangam.p2.fk.*`), dropped, and re-created with identical names and definitions after the conversion with `foreign_key_checks` on (MySQL re-validates the rows; SL-94: one-table-at-a-time conversion fails with error 3780). A table whose widest index would exceed 3,072 bytes is skipped together with its whole FK-linked group and logged | `.../mysql/MysqlUtf8mb4Patch.java`, changeset `P-2-mysql-utf8mb4` | D-04: 4-byte characters cannot be stored in engine string columns | yes |

Upstream PRs to offer: MySQL create/upgrade scripts with `datetime(3)` and `utf8mb4` (as the MariaDB scripts already do).

### SG-09: internal behaviours with no public API, pinned by tests

Operaton 2.2 has no public API or extension point for these behaviours (checked: `ProcessEngineConfiguration`,
`ProcessEnginePlugin`, the command-interceptor, history, calendar and job-handler SPIs expose none of them). Each is
pinned by `EngineInternalsPinTest`, so an upgrade that changes it fails the build:

| Internal behaviour | Relied on by | Pin test |
|---|---|---|
| I-7 `DbEntityManager.invokeOptimisticLockingListeners`: last listener's result wins | adapter fetch (lost race = not fetched) | `i7_lostFetchRaceIsSilentAndExclusive` |
| I-8 `CommandContext.tryCloseInternal`: close listeners fire before `flushSessions` | L2 flush backstop | `i8_flushBackstopTakesRootLockForPlainEngineCommands` |
| I-9 `TimerEntity.calculateNewDueDate` uses the `cycle` calendar as a `CycleBusinessCalendar` | DST-safe cycle calendar | `i9_i10_cycleCalendarAndFollowUpScheduling` |
| I-10 `TimerEntity.preExecute` schedules the follow-up before the handler | `TimerGuard` suppression | `i9_i10_cycleCalendarAndFollowUpScheduling` |
| I-17 `CronTimer.parse` (cron-utils `SPRING53`, shaded) and its evaluation | `ZonedCron` (cron in the timer zone) | `i17_cronParsedAndEvaluatedAsOperatonDoes` |
| I-18 custom session factories replace the built-in manager of the same session type; the Operaton `TaskManager` methods Sangam overrides (`insertTask`, the five `updateTaskSuspensionStateBy*`) and the ones its overrides call (`findTasksByQueryCriteria(TaskQueryImpl)`, `TaskQueryImpl()`, the `CommandContext` authorization/tenant-check getters and setters, which really switch the checks) keep their signatures | B-26 tenant-scoped creation, one Sangam TaskManager | `i18_customSessionFactoriesReplaceTheBuiltInManagers` |
| I-19 `JobRetryCmd.shouldDecrementRetriesFor` spares only `OptimisticLockingException`; `executeJob` failures run the configured failed-job factory | B-16 / SL-89 retry kept on transient conflicts | `i19_retryIsKeptOnlyForOptimisticLockingFailures` |

## Upgrade checklist (every Operaton minor)

1. Re-run P-1/P-2 detection (`secondPrecisionColumns`, `utf8mb3Tables`) after the upgrade scripts.
2. Re-read `DbEntityManager.invokeOptimisticLockingListeners` (I-7) and `CommandContext.tryCloseInternal` (I-8).
3. Check that `TimerEntity.calculateNewDueDate` still calls the `cycle` calendar and that `preExecute` still precedes the handler (I-9, I-10).
5. Re-run `StrictExclusiveRoutingH2Test` (B-24 relies on the gateway behaviour class and the `condition`/`default` properties).
6. Re-run `EngineInternalsPinTest.i17_cronParsedAndEvaluatedAsOperatonDoes`: `ZonedCron` uses the cron-utils copy shaded into operaton-engine (I-17).
4. Re-check the `TEXT_` column sizes per dialect (B-7) and the H2 `BLOB` type in PostgreSQL mode (`DatabaseGuard.prepareH2`).
7. Re-run `EngineInternalsPinTest.i18_customSessionFactoriesReplaceTheBuiltInManagers` and `i19_retryIsKeptOnlyForOptimisticLockingFailures` (I-18 session factories and TaskManager signatures, I-19 retry semantics), and `EnginePatchLedgerGuardTest` (allow-lists below).
