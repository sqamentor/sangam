# sangam-engine: engine behaviour changes (patch ledger)

Base: `org.operaton.bpm:operaton-engine:2.2.1` from Maven Central, used **unchanged as a dependency** (ADR-D-16).
Upgrade 2.2.0 -> 2.2.1 (UP-L1L2, 2026-11-17): patch release; consumer poms (operaton-bom, operaton-root, operaton-engine-dmn)
differ only in version and joda-time 2.15.0 -> 2.15.1, so the FEEL pins (SG-27) are unchanged. The javap evidence below
was taken on 2.2.0; the pin tests (`EngineInternalsPinTest`, upgrade checklist) were re-run on 2.2.1 (see the UP-L1L2 report).
This ledger records every place where Sangam changes engine behaviour, so each upgrade can re-check it.

## Summary

| Kind | Count |
|---|---|
| Engine source or bytecode patches | **0** |
| Engine schema patches (DDL on `ACT_*` after the engine created them) | **2**: P-1, P-2 (MySQL only) |
| Behaviour changed through public extension points | B-1 … B-50 |
| Internal (`impl`) classes used | I-1 … I-30 (sangam-engine); every file that uses one, in any module, is on allow-list A or B |
| Reflection | **2** reads of a protected engine field, each failing closed and pinned by a test: `DmnBusinessRuleTaskActivityBehavior.callableElement` (`deploy/SangamBpmnParseListener.callableElementOf`, SL-13: a deployment fails loudly); `AbstractQueryVariableValueCondition.wrappedQueryValue` (sangam-packs `packs/engine/DecimalValueSerializer.operatorOf`, B-37: a decimal query is refused; the same read, through that method, refuses a pattern query on a local date, B-47) |

## Schema patches

| ID | What | Where | Why | Re-check on upgrade |
|---|---|---|---|---|
| **P-1** | MySQL: every `ACT_*` `datetime`/`timestamp` column with precision 0 → precision 3 (66 columns in 2.2.0) | `sangam-persistence/.../mysql/MysqlDatetimePrecisionPatch.java`, changeset `P-1-mysql-datetime-precision` in `db/changelog/sangam-engine-patches.xml` (runAlways), run by `SangamEngineConfigurer.afterBuild` | D-03 / FC-30: a lease was re-offered 200 ms early and a timer fired 300 ms early (spike ledger, MySQL (2)) | yes: upgrade scripts may add second-precision columns; the patch is idempotent |
| **P-3** (optional) | `ACT_HI_*` (9 high-volume tables) partitioned by `REMOVAL_TIME_` on PostgreSQL / Oracle / SQL Server; PostgreSQL drops the `ID_` PK in favour of a plain index | `sangam-persistence/.../sangam-history-partitioning.xml` (context `partitioned-history`), run by `SangamSchema.applyHistoryPartitioning` / setting `partitionedHistory` | IR-8, R29: cleanup and retention at volume | yes: engine upgrade scripts that add unique indexes to these tables fail on PostgreSQL |
| **P-2** | MySQL: every `ACT_*` table in utf8mb3 → `utf8mb4 / utf8mb4_bin`. String FKs touching the converted tables (46 in 2.2.0) are read from `information_schema`, journaled in `ACT_GE_PROPERTY` (`sangam.p2.fk.*`), dropped, and re-created with identical names and definitions after the conversion with `foreign_key_checks` on (MySQL re-validates the rows; SL-94: one-table-at-a-time conversion fails with error 3780). A table whose widest index would exceed 3,072 bytes is skipped together with its whole FK-linked group and logged | `.../mysql/MysqlUtf8mb4Patch.java`, changeset `P-2-mysql-utf8mb4` | D-04: 4-byte characters cannot be stored in engine string columns | yes |

Upstream PRs to offer: MySQL create/upgrade scripts with `datetime(3)` and `utf8mb4` (as the MariaDB scripts already do).
