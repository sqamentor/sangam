# sangam-channels

Conversations, bots, messenger adapters, inbound mail, polled inbound channels, and SAP and ServiceNow connectors through the connector SPI. Independent implementations from public API documents. No vendor library or artwork is included.

**Evidence level:** compiled, with `ChannelsTest` run on H2 and loopback simulators. Never run against a real Teams, WhatsApp, WeChat, Matrix, Slack, Microsoft Graph, ServiceNow, SAP or Azure endpoint. The simulators and fakes are written from the same reading of the public documents, so they cannot reveal a misreading. The IMAP source has not been run at all. The M-071 additions (Wave 3) have tests written but **not yet run** (`MessengerProvidersTest`, `InboundProvidersTest`, `SapRfcAndODataTest`, `GraphMailSourceTest`, `ConversationIndexAndRetentionH2Test`). JCo itself is never on the build path, so `JcoRfcClient` is exercised only for the absent-JCo path.

## Integration notes

- **Tables:** the `ChannelsSchema` tables (`CH_CONVERSATION`, `CH_PARTICIPANT`, `CH_MESSAGE`, `CH_OPT_IN`, `CH_INBOUND_SEEN`, `CH_POLL_CURSOR`) are in the persistence generator and its five baselines (`sangam-persistence/tools/generate_changelogs.py`, `sangam-0001-baseline.sql`). `CH_MESSAGE_GRAM` (the M-071 search index) is changeset 0043-07 of the generator. A development database whose channel tables were created before it needs that table too (the development schema creates the channel tables only when `CH_CONVERSATION` is missing).
- **REST validation:** `JdbcRegistryAdapter.CHANNELS` accepts `MATRIX`, `TEAMS`, `SLACK`, `WHATSAPP` and `WECHAT`. `ChannelRuntime` builds all five; the entry fields per channel are in its Javadoc (`tokenRef`, `apiBase`, `phoneNumberId`, `appId` + `appSecretRef`, `clientId` + `clientSecretRef` + `tokenUrl`, `templates`).
- **Server wiring** (sangam-server `ChannelsWiring`, `ChannelsScheduler`, `ChannelRuntimeBinder`; off unless `sangam.modules.channels.enabled=true`):
  - Webhook endpoints: sangam-rest `ChannelHooksController` at `/api/v1/hooks/channels/{tenant}/{whatsapp,wechat,teams,slack}` and `.../matrix/transactions/{txnId}`; media is queued on the inbox row and worked by `ChannelMediaWorker` (`sangam.channels.media.threads` default 2, `sangam.channels.media.poll` default PT5S, `sangam.channels.media.lease` default PT10M). It verifies first, dedupes in `CH_INBOUND_SEEN`, maps through `OptInRegistry`, then calls `BotBridge.onInbound`.
  - `ConversationService` with the live hub `ChannelsLiveHub`, served as a server-sent event stream (`GET /api/v1/channels/conversations/{id}/stream`, not a WebSocket) across nodes: a payload-free PostgreSQL notification (`sangam_channels`, the M-005 `WakeupListener`) makes every node catch up its open conversations with `messagesFrom`, re-reading `sangam.channels.stream.catch-up-window` (default 2 minutes) behind the newest message time it has seen, and the same catch-up runs with the comment heartbeat (`sangam.channels.stream.heartbeat`, default 30 s). `Last-Event-ID` replays through `since`. Delivery is at least once; the client drops repeats by message id. Other databases have no notification: other nodes catch up on the heartbeat. The separate `sangam_channels` channel is an integrator decision: it costs one more dedicated database connection per node (beside the relay's `sangam_outbox` listener) and in return chat traffic never wakes the worker long-polls; a file-system `DocumentStore` (`sangam.channels.documents-dir`); the malware scanner bean if present (without one, attachments are refused unless `sangam.channels.allow-unscanned=true`); and the R19 `mayJoin` check.
  - One leader-elected scheduler for `InboundMail.poll` (IMAP and Microsoft Graph) and every `PolledChannels.*.pollOnce` (file, SQL, Service Bus), each with `Receiver.of(InboundEventProcessor)`, plus per tenant a refresh of the channel runtime and a daily `ConversationRetention.runOnce` (`sangam.channels.retention.period`, `sangam.channels.retention.enabled`). A poisoned mail is audited as `INBOUND_MAIL_POISON`; the `Poison` port is not bound to `PoisonInbound`.
  - `ChannelRuntime` connectors are registered in `ConnectorRegistry` per `conversation-channels` registry entry, with a per-tenant egress policy (`sangam.channels.egress.<tenant>`, deny all by default) and the server's `SecretResolver`. The Bot Framework key set is fetched outside `WebhookVerifiers` (`BotFrameworkKeys`, `sangam.channels.teams.jwks-uri`). Provider token endpoints and media hosts must be on the same egress list.
- **Screens:** `sangam-ui` `src/modules/platform.tsx`, page `/m/channels`: inbound channel status (`/channels/status`), a conversation view (message search, open by id, create, send, attach) and opt-in register and withdraw. The same conversation panel is on the case page (`areas/tasklist/StartAndCases.tsx`). The UI polls messages every 10 seconds; it does not use the event stream. Not built: a channel admin screen of its own (channel entries are registry documents), and the Teams tab and task module (NG-11).

## Licence review: SAP JCo (NG-15)

SAP JCo (`sapjco3.jar` plus its native library) is SAP proprietary software that a customer obtains from SAP under its own SAP licence. It is **not** a dependency of any Sangam module. The build never downloads it, and it is never in an image, the fat jar or a release bundle (the same rule as the LIC-2 Oracle driver). `JcoRfcClient` names no JCo class at compile time and loads `com.sap.conn.jco.*` by reflection at run time; `SapRfcAndODataTest.noJcoClassIsOnTheBuildPath` keeps it that way.

Customer steps:
1. Put `sapjco3.jar` in `/opt/sangam/drivers` (on `loader.path`) and the native library on `java.library.path`.
2. Allow the SAP host on the tenant egress list as `https://<host>` (JCo opens its own socket, so this is a host-level check without the HTTP transport's DNS pinning).
3. Keep the RFC user's password behind a secret reference.

Without JCo, every RFC call fails with `SAP_JCO_NOT_AVAILABLE` before anything is sent.
