## 114. veraPDF runs as a separate validator, Rhino stays out of the server (2026-11-12T14:58:05Z, owner via AskUserQuestion)

Question: veraPDF 1.30.4 (decision 94) depends on org.mozilla:rhino 1.7.15.1 to evaluate its validation-profile rules; LIC-10 / D-8 keep Rhino out of the default server build and the enforcer (SL-106) refuses it. Answer (recommended option): veraPDF runs in its own small container, like the script worker; the server sends it the PDF bytes and reads the report. Rhino never enters the server or its fat jar. Until the validator service exists, the server has no validator and PDF output answers 422 FORMAT_NOT_AVAILABLE (fail closed, never an unvalidated PDF). Consequences: sangam-server/pom.xml does not depend on validation-model-jakarta; the in-process VeraPdfValidator in sangam-integration (optional dependency) becomes the core of the validator service; a remote Validator client in the server is Wave 4 work under M-081; LIC-10 and the fat-jar guard in server.Dockerfile stay unchanged.

## 115. API contract versions are stored only while the package is DRAFT (2026-11-12T15:04:05Z, owner via AskUserQuestion)

Question (W3-B, M-068): a contract version could be stored after its package was submitted or approved, and an unversioned operationRef pins the newest version at deploy, so an unreviewed contract could enter a deployed model. Answer (recommended option): PUT of a contract version answers 409 unless the package is DRAFT, matching the hash freeze at submit (R43). Every newly stored version writes the audit event API_CONTRACT_STORED in the same transaction (an identical re-send that returns the stored version writes none); an audit failure rolls the store back.
