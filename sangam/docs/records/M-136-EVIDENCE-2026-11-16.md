## Root cause fixed during the run

Operaton 2.2.0 `ExternalTask.xml` disagrees with itself about when a lock has expired:
- `selectExternalTasksForTopics` (fetch and lock, line 220) treats a task as free when `LOCK_EXP_TIME_ <= now`.
- The `notLocked()` query (lines 379-380) requires `LOCK_EXP_TIME_ < now`, strictly.

The Sangam lease sweep also ends a lease at `expires_at_ms <= now` (`SangamLeaseTable.lockExpired`), and a re-offer leaves the Operaton lock in place (`LeaseExpiry.apply`).
`EngineObserver.lease` used `notLocked()`. A task whose lease expired exactly at the sweep instant was re-offered and fetchable, but the observer did not see it.
The observer now applies the fetch's own rule on the adapter clock.
Before-fix: the same code without that change gave 6 of 37 failures (log `build7.log`). The replay stopped at seq 3, so seqs 3 to 8 were never asked for.

## Limits and NOT_RUN

- **NOT_RUN:** Oracle and SQL Server (W4-E, test phase). Only H2 ran (MODE=PostgreSQL).
- A TIMEOUT is replayed as a one-millisecond lease taken one millisecond before the recorded sweep, so it expires exactly at the sweep instant. The capture holds no input for when the lease was taken, and nothing else is recorded in between.
- Instants go back to the engine as `java.util.Date`; integers widen to `Long`.
- An expiry that the policy HOLDs (class `c`, or undeclared) is not in this scenario.
- These are UNSUPPORTED by design: a message start event and a standalone decision (no execution), CMMN, forms, scripts, Java delegates and expressions, connectors, and async continuations.
- The product version is null in development builds.
- REST and UI do not expose replay, so nothing was rewired there.
