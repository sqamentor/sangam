# sangam-rest

The Sangam API, `/api/v1` (ARCHITECTURE.md §4), written as Spring MVC controllers. The controllers call **service port interfaces** (`org.sangam.rest.port`), and the module ships default adapters for every port. Owner: WS-REST.

- **Contract:** `api/sangam-api.yaml` (OpenAPI 3.1.0). It has 283 paths, 360 operations, 255 schemas and 156 tracked commands. This includes every UI proposal from `sangam-ui/src/api/endpoints.ts`. It is packaged at the classpath root, and sangam-server serves it at `/api/v1/openapi.yaml`.
  - WS-SDK and WS-UI generate their clients from it.
  - The YAML is generated by `api/gen_openapi.py`: run `python -E -X utf8 api/gen_openapi.py api/sangam-api.yaml`. Make changes in the script and regenerate, so that hand edits are not lost on the next run.
- **Consistency checks:** these were run at build time.
  - Every spec path and method (all 324) has a controller mapping, and every mapping is in the spec.
  - `web/CommandCatalog` is **read from the packaged `sangam-api.yaml`**: every operation with `x-sangam-idempotent: true` and an `x-sangam-command-type`. The R41 command list therefore cannot drift from the contract.
- **Build:**
  - `mvnw.cmd -q -B -DskipTests -pl sangam-rest -am install`.
  - The module compiles without the other modules (sangam-engine, -security, -integration, -flowable-ports, -packs). It needs only sangam-core, the Operaton 2.2.0 engine API and Spring Framework 7.0.10 (Spring Boot 4.1.2 BOM).

## Cross-cutting behaviour

- **Errors.** Every error is `application/problem+json` with `type`, `title`, `status`, `detail`, `instance`, `code` and `traceId`, plus extensions. The type URI is `https://sangam.dev/problems/<code-in-kebab-case>`. A stale worker lease returns `409` with code `STALE_LEASE` and type `.../stale-lease`. Codes follow X.4.0.4 and X.2.2.6.
- **Idempotency-Key (R41 / X.2.2).**
  - **Fingerprint.** It is computed with the core `IdempotencyStore.fingerprint` over the command type, method, path template, path parameters, the semantic query, `If-Match`, `X-Sangam-Acting-For-Seat` and the canonical JSON body. Decimals in the body are kept as strings; multipart bodies are fingerprinted by part digests.
  - **Claim.** The claim runs in its own transaction.
  - **Execution.** The controller runs inside one Spring transaction, which the Operaton engine joins. `COMPLETED` is written as the last write of that transaction (L6, P-1), and the response is buffered until commit.
  - **Failures.** Deterministic 4xx results are stored as `FAILED_FINAL`. Transient errors and 401/403 are not stored.
  - **Replays.** A replay re-checks authorization (`PermissionPort.mayReplay`) and carries `Idempotent-Replayed: true|compacted` and `Idempotency-Key-Expires`. Each replay is audited (`IDEMPOTENT_REPLAY`).
  - **Government profile.** With `sangam.rest.government-profile=true`, a missing key returns `400 IDEMPOTENCY_KEY_REQUIRED` for the commands listed in X.2.2.1.
  - **Metrics:** `api.idempotent.replays`, `api.idempotency.conflicts{reason}` and `api.idempotency.in.progress`.
- **Lists.** Lists take `?page=&size=` (size 1–500) and return `X-Total-Count`. Counts are capped at `sangam.rest.count-cap` (default 10 000): above the cap the header shows the cap and `X-Total-Count-Capped: true` is set (A-16). The adapter checks whether the cap is exceeded with a `listPage(cap, 1)` probe instead of a full count.
- **Tenant.** The tenant comes only from the authenticated `SangamPrincipal` (claim `tenant`, VI.4 rule 6). Every query is tenant-scoped, and a get-by-id on an object of another tenant returns 404.
- **OpenTelemetry (R13, §1.8).** Spans carry `sangam.tenant`, `enduser.id`, `sangam.seat`, `sangam.idempotency_key`, `sangam.business_key`, `sangam.operation_id`, `sangam.process_instance_id`, `sangam.command_type` and `sangam.work_id`. The same values go into the SLF4J MDC.
- **Metrics for the deploy dashboard.** `sangam.lease.stale` (every `STALE_LEASE` response) and `sangam.lease.extended` (heartbeats) appear in Prometheus as `sangam_lease_stale_total` and `sangam_lease_extended_total`.

## Defaults versus production modules (integration notes)

Each default can be replaced by declaring a bean of the port type. sangam-server now does that for the engine, security, integration, ports and packs; the current map is in `sangam-server/README.md` "Integration notes". The table below describes the defaults, which apply when a module is switched off.

**Nothing is kept in memory.** Every default adapter persists its state in product tables (sangam-persistence changesets 0016-*):
- **`REST_DOCUMENT`** (typed, tenant-scoped JSON documents, via `support/DocumentStore`): registries, low-code pages, data objects and records, alerts, identity providers, service principals (secret hash only), users and group members, notifications, case and package comments, Git configuration, portal drafts and grievances, ops claims and notes, notification failures, topic pauses, export-job metadata, and the module-disabled admin default.
- **`REST_BLOB`** (`support/BlobStore`): audit export files and reconciliation evidence.
- **Reused module tables:** `SEC_POWER_TABLE` (power tables), `SEC_SOD_EXCEPTION`, `AUTH_POLICY_VERSION`, `PACKAGE_VERSION` (packages), `EVT_CHANNEL_DEF` / `EVT_EVENT_DEF` (event registry default), `FORM_DRAFT` (drafts), `INSTANCE_LINK` (explicit links), `DEBUG_BREAKPOINT`, `PORT_BATCH` / `PORT_BATCH_ITEM` (batches), and `LEGAL_HOLD` (in the server's ports document bridge).

Only caches and runtime telemetry stay in memory (form-version cache, conformance graph, worker heartbeat statistics).

At start-up, RUNNING batches and QUEUED or RUNNING export jobs resume.

Without the owning module, these return 501 `CAPABILITY_NOT_INSTALLED`: directory sync (sangam-security), Git pull/push (sangam-packs, R69 stage E) and REST-backed data objects (sangam-integration). Reconciliation lookup and notification resend are bound to sangam-integration in `sangam-server` (`OpsIntegrationWiring`).

PDF/A and DOCX rendering is not available by default.

Tables these adapters need: `AUDIT_EVENT`, `AUDIT_PAYLOAD`, `ROOT_SEQ`, `IDEMPOTENCY_RECORD`, `RECONCILIATION_ITEM`, `TOMBSTONE`, `OUTBOX`, `OUTBOX_DELIVERY` and `INBOX` (core `Schema`), plus the `LeaseTable` tables. For h2, sangam-server creates them with core `Schema`; in production they come from the sangam-persistence Liquibase changelog.

Conventions used by the adapters, which packs and models must follow: the process variables `sangamInitiator`, `sangamCaseVersion`, `sangamMaterialFields`, `sangamSodExclude`, `sangamActors`, `sangamDecision`, `sangamSeatId`, `sangamFormVersion` and `sangamPackageHash`, and the task-local variable `sangamSod=strict`.
