Related finding, **FIXED (SL-37 follow-up):** `OperatonClock.register` counted engines per JVM and nothing released the count when a Spring context closed. The starter owns and closes the engine, and only `OperatonEngineAdapter.close()` decremented, so the server never did. A global `unregister()` could also decrement another engine's slot. Fix: `register` returns an idempotent, thread-safe `Registration` handle owned by the configurer (`SangamEngineConfigurer.releaseEngineSlot()`). It is released by adapter close, by a failed build, and by the server's `EngineConfigurerHolder.destroy()` on context shutdown. Tests: `OperatonClockRegistrationTest` (2, sangam-engine) and `EngineSlotReleasedOnContextCloseTest` (two server contexts one after the other with the flag off; fails without the fix). The flag is removed from `EngineRestRoleGateTest`. The four h2 `@SpringBootTest` classes that relied on a cached context now carry `@DirtiesContext`, so no engine outlives its class. The engine-module tests keep the flag where they build engines programmatically.
