## 1. The key finding: what the 43 and the 74 actually are

1. **All 43 `SEC_TENANT` reads are SL-43 quota-override reads, not tenant-isolation reads.** `JdbcTenantQuotas.limit()` → `overrides()` → `QuotaWiring` source → `TenantAdminService.find`. Tenant-isolation reads are the 6 identity-stamp sub-selects (`ResolvedIdentityCache.java:123-124`), counted under their own key.
2. **They exist only because the probe ran the acceptance profile.** `AbstractAcceptanceIT.java:115` sets `sangam.quotas.override-ttl=0s` ("read without caching so a test's override applies at once"). Production is `30s` (`application.yaml:147`, `QuotaWiring.java:123`). With 30 s, `JdbcTenantQuotas.java:240-242` serves every one of them from the in-memory cache: about 0 per lifecycle, one read per tenant per node every 30 s.
3. **The probe trees predate the SL-43 fix (460c95b).** The register says "both trees deadlock the pool through SL-43", and the pre-fix wiring confirms it: in `460c95bf^:QuotaWiring.java` the source is `ptx.inTransaction(c -> s.tenants().find(...))` on `Transactions.of(ds)`. So each of the 43 reads was **its own main-pool transaction: SELECT + COMMIT**.
   * **Of the 74.3 commits, 43 are those override reads.** The other ~31.3 are real business and identity transactions.
   * After 460c95b, override reads inside an engine command run on the caller's connection (`JdbcTenantQuotas.java:244-248`, `QuotaWiring.java:130-132`), with no commit of their own. Filter reads (no ambient transaction) run on the leaf `sangam-quota` pool (`:268`), which `StatementCounter` does not wrap.
   * **On the current tree the register's "74 commits" is already about 31 main-pool commits.**
4. **Where the 43 come from, per lifecycle (TTL 0).**
   * 33 come from the engine path: `TenantQuotaEnginePlugin.java:76` (start `acquire`) and `:83/:97` (`checkVariables` → `limit(VARIABLE_BYTES)` on **every** outermost tenant-bound command, including pure queries).
   * 10 come from the filter path: `TenantQuotaFilter.java:55` (API_CALLS, ×6) and `:58` (DOCUMENT_BYTES on every JSON POST with a body: start, fetch, work.complete and task.complete, ×4).
   * 33 + 10 = 43, which matches the measurement.

## 4. Side findings for the owner (not SG-15, not coded)

* `OperatonTaskAdapter.checkSod` (`:821`) runs `tx.inNewTx(audit.record(...))` inside `complete()`'s `tx.inTx`. That is a second main-pool connection requested while one is held: the SL-43 pool-deadlock pattern, on the SoD-violation path only. Under concurrent violations with a saturated pool it waits for `connectionTimeout`.
* `TenantQuotaFilter.isUpload` (`:77-81`) treats every JSON POST/PUT/PATCH body as an upload for DOCUMENT_BYTES. The SL-43 row calls this "body size", so it is intended. Noted only as the source of reads in #3.
* The register text "74 commits and 43 `SEC_TENANT` reads per lifecycle" describes a pre-SL-43 tree under a test-only TTL; see §1.

## 5. Phase 2: coded change

**`sangam/sangam-server/src/main/java/org/sangam/server/bridge/TenantQuotaEnginePlugin.java`, `QuotaInterceptor.checkVariables` (lines 96-131).**

Before:

```java
long max = q.limit(tenant, QuotaLimit.VARIABLE_BYTES);   // every outermost tenant-bound command
if (max < 0) return;
... for each cached VariableInstanceEntity: if written -> size -> checkSize if over
```

After:

```java
CommandContext ctx = Context.getCommandContext(); if (ctx == null) return;
for each cached VariableInstanceEntity: if written {
    if (!limitRead) { max = q.limit(tenant, VARIABLE_BYTES); limitRead = true; }   // once per command
    if (max < 0) return;                     // unlimited: still never loads a byte array to measure
    size -> checkSize if over                // unchanged
}
```

**Test (new):** `sangam/sangam-server/src/test/java/org/sangam/server/bridge/QuotaVariableCheckReadsH2Test.java`, real Operaton in-memory H2 engine with the production plugin and a counting `TenantQuotas`. 8 tests:

1. `commandsThatWriteNoVariableReadNoVariableLimit`: queries, `getVariables`, identity links and claim make 0 limit reads.
2. `aCommandWritingVariablesReadsTheLimitOnceAndStoresThem`: 1 read for 3 values; all stored.
3. `anOversizedNewValueIsRefusedAndTheCommandRollsBack`: 413 path, VARIABLE_BYTES; neither value stored.
4. `anExistingValueUpdatedToAnOversizedOneIsRefusedAndKeepsItsOldValue`: the dirty persistent path.
5. `everyStartTakesAStartPermitWithOrWithoutVariables`: STARTS acquire 1 each; variable read 0 or 1.
6. `aRefusedStartCreatesNothing`: instance count unchanged.
7. `anUnlimitedTenantStoresAnySizeWithoutASizeCheck`.
8. `withoutABoundTenantNothingIsCountedOrRead`.

Not run (gates are compile only). Run in the test phase together with `EngineRestTenantRefusalTest`, `TenantQuotaIT` and `QuotaPoolDeadlock*`, which cover the same plugin end to end.
