# M-106 evidence: extension points for the Stage D engine patches (B32, W2-D, 2026-11-12)

Scope: evidence only (BACKLOG-0.1.0-MASTER §1 M-106, P3-050; ADR-D-16 "Operaton as a dependency, extended through plugins
only"). For each planned engine source patch, this file records whether Operaton 2.2.0 already has an extension point,
so that a patch is made only where none exists. Nothing was patched; the engine jar is unchanged.

Base: `org.operaton.bpm:operaton-engine:2.2.0` from the local Maven repository (`~/.m2/.../operaton-engine-2.2.0.jar`,
no sources jar). Tools: `javap -p` / `javap -c -p` from JDK 25.0.5 (`.tools/OpenJDK25U...`); the MyBatis mapping
XML files were read from the jar (`jar xf` into the session scratchpad). Each item below says the class, method and
bytecode offset (or mapping line) that the claim rests on.

Patch ids are the ids in section D "Operaton weaknesses" of `spike/results/FLOWABLE-INTO-OPERATON.md` ("FIO D-n"),
as listed in `sangam/sangam-engine/README.md:256` and `BACKLOG-P3-2026-11-12.md` P3-050.

## FIO D-19: concurrent external-task fetch

Current state: `ExternalTask.xml` (jar `org/operaton/bpm/engine/impl/mapping/entity/ExternalTask.xml`), select
`selectExternalTasksForTopics` (line 174) has no `FOR UPDATE` / `SKIP LOCKED` on any dialect: concurrent fetchers
compete through the `REV_` optimistic lock. Sangam's interim route is the per-topic `SANGAM_FETCH_LOCK` row lock plus
the OLE listener (README note 22, PATCHES.md I-7).

Evidence for an extension point:
1. `ExternalTaskManager.selectExternalTasksForTopics(...)`: `ldc "selectExternalTasksForTopics"` then
   `DbEntityManager.selectList(String, ListQueryParameterObject)` (javap -c, offsets 96 to 100).
2. `DbSqlSession.selectList(String, Object)` and `selectList(String, Object, int)`, `selectById`, `selectOne`,
   `lock`, `executeUpdate`, `executeDelete`, `executeNonEmptyUpdateStmt` and `insertEntity` all call
   `DbSqlSessionFactory.mapStatement(String)` first (javap -c `DbSqlSession`, 10 call sites).
3. `DbSqlSessionFactory.mapStatement`: returns `statementMappings.get(statement)` when there is one, else the
   statement unchanged (javap -c, offsets 0 to 32).
4. `statementMappings` is a per-instance field with a public setter `setStatementMappings(Map)`.
   `setDatabaseType` assigns it from the static `databaseSpecificStatements` per database type (offsets 0 to 18), so a
   per-engine copy with one extra entry changes only that engine, not the JVM-wide static map.
5. The engine's MyBatis `SqlSessionFactory` is reachable through `ProcessEngineConfigurationImpl.getSqlSessionFactory()`;
   its `org.apache.ibatis.session.Configuration` accepts an additional mapper through MyBatis' public
   `XMLMapperBuilder` (MyBatis API, not an engine internal).
6. The job side shows the shape Operaton itself uses for this: `Job.xml selectNextJobsToExecute` (line 178) with
   `FOR UPDATE SKIP LOCKED` under `parameter.skipLocked` (line 232), plus `_mssql` (UPDLOCK, ROWLOCK, READPAST,
   line 263), `_db2` (line 372) and `_oracle` (line 381, no row limit, the caller cuts the cursor; line 439
   `FOR UPDATE SKIP LOCKED`) variants selected per database type.

Route (for W4-A): a Sangam statement `sangamSelectExternalTasksForTopicsSkipLocked` (per dialect, modelled on the
`selectNextJobsToExecute*` variants, `FOR UPDATE OF RES SKIP LOCKED` where joins are present) added to the engine's
MyBatis configuration after the build, and `statementMappings` of this engine's `DbSqlSessionFactory` mapping
`selectExternalTasksForTopics` to it. The "throw instead of ignore" half is already done through the
last-listener-wins rule (PATCHES.md I-7, pinned by `EngineInternalsPinTest.i7_...`).

Open points: (a) whether `isUseSharedSqlSessionFactory` (static `cachedSqlSessionFactory`) is on in any embedding
(then the added statement is JVM-wide, which is harmless because only the mapped engine uses it); (b) the authorization
join branch of the statement (Sangam runs with engine authorization off, B-14); (c) DB-matrix proof on the 4 Tier-1
databases in the test phase.

## FIO D-10: per-engine clock

Current state: `OperatonClock` is the only Sangam user of `ClockUtil` and enforces one engine per JVM
(PATCHES.md I-5, README note 13).

Evidence:
1. `org.operaton.bpm.engine.impl.util.ClockUtil` has no fields. `getCurrentTime()` -> `now()` ->
   `org.joda.time.DateTimeUtils.currentTimeMillis()`; `setCurrentTime(Date)` -> `DateTimeUtils.setCurrentMillisFixed`;
   `offset(Long)` -> `setCurrentMillisOffset`; `reset()` / `resetClock()` -> `setCurrentMillisSystem` (javap -c).
2. Joda-Time is a compile dependency of operaton-engine 2.2.0 (`joda-time:joda-time:2.15.0`, pom lines 638 to 643).
   `DateTimeUtils` has `private static volatile MillisProvider cMillisProvider` and a public
   `setCurrentMillisProvider(MillisProvider)` (javap, joda-time 2.15.0).
3. 46 classes under `org/operaton/bpm/engine/impl` reference `ClockUtil` (byte search of the extracted classes),
   among them `AcquireJobsCmd`, `JobManager`, `TimerEntity`, `DurationHelper`, `CycleBusinessCalendar`,
   `ExternalTaskEntity`, `LockExternalTaskCmd`, `DefaultHistoryEventProducer`, `HistoryCleanupHelper`,
   `MetricsCollectionTask`. All of them go through `ClockUtil`, so all go through the Joda provider.

Route: a `MillisProvider` that returns the clock of the engine of the current command
(`Context.getProcessEngineConfiguration()`, a ThreadLocal stack, PATCHES.md I-6), and the system clock when there is
none. That gives a per-engine clock without an engine source change.

Why below 97%: (a) the provider is JVM-wide, so any other Joda-Time user in the JVM sees it (only inside an engine
command, by construction); (b) reads outside a command context (for example `MetricsCollectionTask` on its timer
thread, the job acquisition loop's wait computation) would get the system clock; whether any of them must follow a
test clock needs a proof test per reader; (c) `OperatonClock.register` and the one-engine-per-JVM guard would change.
Question for the owner, tied to Q-02: is several engines per JVM (Q-02 option B) still wanted? Under option A
(one engine per JVM) D-10 is not needed at all.

## FC-24: job hand-off and separate timer acquisition

Evidence that it is already done without a patch, in `sangam-flowable-ports`:
- `ports/jobs/SplitJobExecutors.java:47-54`: the engine's executor acquires non-timer jobs only, through
  `setAcquireJobsCmdFactory(n -> new FilteredAcquireJobsCmd(...NON_TIMERS...))`; a second `DefaultJobExecutor`
  acquires timers only; an optional global acquire lock; optional `AsyncJobHandOffInterceptor` (post command
  interceptor) for the post-commit hand-off.
- Operaton API used: `JobExecutor.setAcquireJobsCmdFactory(AcquireJobsCommandFactory)` and
  `getAcquireJobsCmd(int)` (javap `JobExecutor`), `ProcessEngineConfigurationImpl.setCustomPostCommandInterceptorsTxRequired`.
- The same factory hook is the acquisition extension point for R39 partitioned executors (M-056).

Doc drift to fix (README is W2-J's file): `sangam-engine/README.md:125` says the hand-off / separate timer acquisition
is a Stage D patch, and `:256` lists FC-24 among the engine source patches. Both should point to the ports route.

## FIO D-27: multi-instance compensation without `loopCounter`

Evidence:
- Sangam already replaces Operaton's `compensate` event handler: `SequentialCompensation.EventHandler extends
  CompensationEventHandler` (`sangam-engine/.../deploy/SequentialCompensation.java:110-145`, PATCHES.md B-21, I-14),
  registered through `cfg.setCustomEventHandlers` (`SangamProcessEnginePlugin.preInit`). A multi-instance body is
  passed to Operaton's handler unchanged (`:119-124`).
- `CompensationUtil.createEventScopeExecution(ExecutionEntity)` copies the ending execution's local variables into
  the event-scope execution (`getVariablesLocal()` then `setVariableLocal` per entry, javap -c offsets 82 to 142).
  For a scope activity the inner instance's `loopCounter` would therefore be kept, which does not match the D-27
  observation (E16a #7, D-TENDER) for every model shape.

Route: in the custom handler, or through an end execution listener added by the BPMN parse listener on the inner
activity of the multi-instance body, put the instance's `loopCounter` where the compensation handler can read it.
Why below 97%: the symptom and the bytecode disagree for scope activities, so the failing model shape must be
reproduced first (an H2 test with the E16a #7 model). If the shape is a non-scope task with a compensation boundary
event, the subscription is created without an event-scope execution and the listener route applies.

## FIO D-52: missing BPMN constructs

Evidence:
- `BpmnParse.parseActivities` (javap -c, offsets 412 to 443): for `adHocSubProcess` and `complexGateway` it calls
  `addWarning("Ignoring unsupported activity type", element)` and creates no activity. No parse listener is called
  for them, so a `BpmnParseListener` cannot add them.
- `ProcessEngineConfigurationImpl.setBpmnParseFactory(BpmnParseFactory)` is public;
  `BpmnParseFactory.createBpmnParse(BpmnParser)` is the single method; `BpmnParse.parseActivities` is public and
  `parseActivity` protected, so a subclass can parse a construct Operaton ignores.
- This route is already in use: `sangam-flowable-ports/.../adhoc/SangamBpmnParseFactory.java` installs
  `SangamBpmnParse` (`AD_HOC_TAG = "adHocSubProcess"`, line 28), with `AdHocSubProcessActivityBehavior`
  (PATCHES.md allow-list B).
- No `standardLoopCharacteristics` or `dataStore` string exists in `BpmnParse` (javap -c dump); they are silently
  not parsed, and the same subclass route applies.

Verdict: an extension point exists for each construct; each construct is its own behaviour design (MoSCoW per
R34/R44), not an engine patch.
