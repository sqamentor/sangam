# Patch ledger: Flowable 8.0.0 adapter

Module: `spike/adapter-flowable`. Main file: `src/main/java/org/sangam/spike/flowable/FlowableEngineAdapter.java` (1047 lines in total since the parity fixes of 2026-11-04 evening; 639 before them; 575 before the interface change of 2026-11-04).
Engine setup: `StandaloneProcessEngineConfiguration` plus `DmnEngineConfigurator` and `CmmnEngineConfigurator`. No Spring. The async executor is off by default for BPMN and CMMN and can be switched on (F11, `ContinuationMode.ASYNC_EXECUTOR`). History is synchronous.

**Engine patches: 0.** No Flowable source is changed, and there are no forks, bytecode changes or reflection.
**Workarounds that use internal (`impl`) classes: 5** (F1–F5), about 75 adapter lines in total.
**Workarounds after the interface change (lease fencing, case tasks, activity instance id): 3** (F6–F8), about 50 adapter lines, plus the shared `LeaseTable` (product-api, counted once for both engines, see F6). F2 is replaced by F6.
**Parity fixes of 2026-11-04 (the same fixes the Operaton adapter got as W-9/W-10, plus Flowable-only items): 4 new entries F9–F12, F3 rewritten, one bug fix (correlation, "Fix C1", not a workaround).** About 330 adapter lines, most of them the fetch retry loop and expiry sweep that Operaton's W-9/W-10 also needed (~150 lines there). Of the new entries, **F12 uses an impl class** (`AbstractAsyncExecutor`/`ResetExpiredJobsRunnable`); F9 reads an engine table with plain SQL (schema dependency, not an impl class). ## Q1: can product tables commit in the same transaction as engine state?

**Yes, with workaround F5.** `inEngineTransaction` runs inside `ManagementService.executeCommand`. Engine calls made inside it join the same `CommandContext` (context reuse), and product SQL uses the same JDBC connection.

Tests (each runs on H2 and PostgreSQL 17):
- `q1_productRowAndEngineChangeRollBackTogether`: insert a product row, start a process, flush, and see both rows on the same connection. Then throw. Result: product row 0, process instance 0.
- `q1_productRowRollsBackWhenEngineCommandFails`: product row, start a process, then the engine throws (`completeTask` on an unknown task). Both are rolled back.
- `q1_productOnlyWriteRollsBack`: product row, then throw, with no engine write. The row is rolled back (this needs F5).
- `q1_productRowAndEngineChangeCommitTogether`: both are committed; the product-only commit also works.

Caveat: engine entities are flushed only at command close, after the product SQL. A product insert that fails therefore fails before the engine writes. An engine optimistic-lock failure at flush rolls back the product rows too, as intended.

## Q3: does the external-worker API support the VI.3 lease model?

**Partly.** Flowable offers acquire with a per-call lock duration, complete, bpmnError, fail with retries and back-off (dead letter at 0 retries = INCIDENT), unacquire (release), tenant and user/group filters, and variables returned on acquire.

| VI.3 need | Flowable 8.0.0 | Adapter |
|---|---|---|
| LOCKED with a lease, per-topic duration | Yes (`topic(name, lockDuration)`) | Direct |
| Heartbeat / extend lock | **No API** | F1 (internal entity) |
| Reject calls after the lease expires | **No.** Only the owner is compared | F6 (check against `SPIKE_LEASE.expires_at` in the same command; replaces F2) |
| Lease expiry → AVAILABLE | Only through the async executor's reset thread (which also covers external-worker jobs) | F3 sweep in `fetchAndLock` and `executeDueJobs`, through the A-10 policy (F12); the async executor's reset is restricted to async/timer jobs (F12) |
| A-10 hold of expired work | No "held" state; dead letter (retries 0) is the closest | F12: HOLD = dead letter, released by `moveDeadLetterJobToExecutableJob` (same job id) |
| Fencing token / `lockVersion` / `attemptId` | **No.** The job keeps the same id across expiry and re-acquire. `REV_` exists internally but is not exposed, and the same `workerId` re-acquiring cannot be told apart from its stale self | **F6** (adapter-owned `SPIKE_LEASE`). Tests (a)–(d) on H2 and PostgreSQL |
| OFFERED → ack two-phase | **No.** Acquire goes straight to LOCKED | Product layer |
| Release (unacquire) | Yes. Needs the workerId and checks it; fails if the job has no owner | `unlockExternal(workId, workerId, lockVersion)`, fenced by F6. A job parked by a retry back-off has no lease and cannot be unlocked by a worker; F3 releases it when the back-off ends |
| fail with retries / back-off | Yes. The back-off parks the job until a reset | F3 |
| outcomeUnknown / UNKNOWN_OUTCOME, cancel-requested in the heartbeat, `effect=irreversible` | **No** | Product layer |
| operationId stable across retries | The job id is stable across fail/expiry, but a new job is created after a BPMN retry loop or migration. No activity instance id on the job | `ExternalWork.activityInstanceId` from `ACT_RU_ACTINST` (F8), stable across expiry (test (c)); operationId itself is built by the product layer (VI.3 rule 4) |

## Async continuation (F11): the honest semantic difference

Flowable 8.0.0's `ExternalWorkerJobCompleteCmd` / `ExternalWorkerJobBpmnErrorCmd` do not move the token. They copy the variables to the job's scope and **move the external-worker job to an executable job** (`JobManager.moveExternalWorkerJobToExecutableJob`, handler `external-worker-complete`, checked in the bytecode). `ExternalWorkerTaskCompleteJobHandler` later copies the variables to the execution (it reads them with a database query) and triggers the execution. There is no public option to run it inside the completion command. Running the handler in the same command would need a mid-command `DbSqlSession.flush()` plus internal `JobManager.execute`; not done, because a mid-command flush is not a supported path and could hide lost updates.

| | Operaton 2.2.0 | Flowable, `AFTER_COMMIT` (default) | Flowable, `DEFERRED` | Flowable, `ASYNC_EXECUTOR` |
|---|---|---|---|---|
| Transactions per completion | 1 (complete + continuation to the next wait state) | **2**: completion, then continuation | 2, the second when `executeDueJobs` runs | 2, the second on an executor thread |
| When `completeExternal` returns | instance at its next wait state | **same** (after the outermost commit) | still at the service task | usually still at the service task (milliseconds later) |
| Continuation throws | the completion rolls back; the worker gets the exception and its lease is intact | completion **stays committed**; lease row already removed; Flowable retries the job (3 retries, then dead letter); counted in `continuationFailures()`; worker call succeeds | same as left | same, on the executor |
| Nested in a caller's Q1 transaction (`inEngineTransaction`) | continuation is inside the caller's transaction | continuation runs **after** the caller's commit, not inside it; on rollback nothing runs (tested) | — | — |
| Latency | one command | completion command + job query + `executeJob` command (one extra commit and two extra round trips) | — | hand-off to executor |

For E3/E9-style experiments: `AFTER_COMMIT` gives the same observable end state as Operaton when `completeExternal` returns, so `executeDueJobs()` after a completion now returns 0 on Flowable (E3's `asyncJobsAfterCompletion` will read 0 on a rerun; it was 1). It does **not** give Operaton's atomicity: a product that relies on "completion and next step commit together" must treat Flowable as two transactions. Latency figures measured with the default mode include the continuation; E9's earlier Flowable `completeExternal` latency (122 ms p50) did not.

## Interface observations

Changed on 2026-11-04 (`product-api`):
- `ExternalWork` now has `activityInstanceId`, `lockVersion` and `attemptId`; `extendLock`, `completeExternal`, `failExternal`, `bpmnErrorExternal` take `long lockVersion`; `unlockExternal(workId, workerId, lockVersion)` is owner-checked. A stale version, a non-owner or an expired lease throws `org.sangam.spike.api.StaleLeaseException` (with a `Reason`), and nothing changes. The adapter's own nested `StaleLeaseException` is gone.
- `startCase(...)` is in the interface. Case tasks go through `queryTasks`/`countTasks`/`claimTask`/`completeTask` (no `queryCaseTasks`); `getInstance` and `cancelInstance` accept case instance ids (F7). `getInstance` returns `null` for an unknown id (tested).
- Tests added on both databases: `fencing_a_staleLockVersionIsRejected`, `fencing_b_callsAfterExpiryAreRejected`, `fencing_c_reacquireAfterExpiryFencesTheOldWorker`, `fencing_d_unlockByNonOwnerIsRejected`, `startCaseAndCompleteCaseHumanTask`.
